# Senior Engineer Task: Upgrade My Existing Login Application to Production-Ready Authentication

## 1. Role and Objective

Act as a Senior Backend Engineer, Application Security Engineer, and Performance Engineer.

I have an existing basic login application consisting of two separate codebases:

- **Frontend:** React.js
- **Backend:** Java Spring Boot
- **Database:** MySQL
- **Deployment:** Cloud environment
- **Load target:** 1,000 concurrent login requests

I will provide my existing frontend and backend source code. Your responsibility is to audit the current implementation, identify weaknesses, and upgrade it into a secure, maintainable, production-oriented application.

**This is an existing application, not a demo or a greenfield project.**

Do not replace everything with a new sample application. Understand the current implementation first, preserve working functionality, and make targeted changes wherever possible.

The frontend and backend must remain separate applications that communicate through REST APIs.

Do not claim the application is production-ready or supports 1,000 concurrent logins until the relevant security tests and load tests have been executed successfully.

### Phase 3: Implement Production-Oriented Authentication

#### A. Authentication and password security

Implement or repair:
- Database-backed user authentication.
- Spring Security integration.
- BCrypt or Argon2 password hashing with an appropriate, benchmarked work factor.
- Generic authentication failure messages.
- Server-side account-status checks.
- Input validation and normalization.
- Secure registration, if registration already exists or is required.
- Password reset using short-lived, single-use tokens, if applicable.
- Logout and session/token invalidation.
- Protection against account enumeration and brute-force attacks.
- Safe handling of malformed requests and unexpected exceptions.

Never store plaintext passwords or reversible password encryption.

Never implement a custom password-hashing algorithm.

Do not expose stack traces, internal errors, password hashes, or sensitive user information through API responses.

#### B. Choose the appropriate session strategy

Inspect the existing authentication mechanism before changing it.

For a browser-based application, evaluate secure server-managed sessions using cookies with HttpOnly, Secure and appropriate SameSite attributes.

If JWT is already required, implement or validate:
- Cryptographic signature verification.
- Expiration and issuer/audience validation where applicable.
- Short-lived access tokens.
- Secure refresh-token storage and rotation.
- Refresh-token reuse detection where supported.
- Logout and revocation behavior.
- Signing-key management and rotation.

Do not store long-lived credentials in localStorage by default.

If cookie authentication is used, implement CSRF protection appropriate to the application.

Do not combine multiple authentication mechanisms unnecessarily. Explain the chosen approach and its trade-offs.

#### C. Frontend requirements

Preserve my existing UI unless a change is necessary.

Implement or repair:
- Email/username and password validation.
- Submit-button loading state.
- Prevention of accidental duplicate submissions.
- Clear, accessible validation messages.
- Generic authentication error messages.
- Network timeout and server-error handling.
- Safe handling of expired sessions.
- Protected routes where applicable.
- Logout and authentication-state cleanup.
- Keyboard accessibility and responsive behavior.
- No secrets, database credentials or signing keys in frontend code.

Do not treat frontend validation as a security boundary. Repeat all security-relevant validation on the backend.

Ensure React never connects directly to MySQL.

#### D. Backend API design

Preserve existing API contracts when possible.

If changes are necessary, document:
- Old endpoint and new endpoint.
- Request and response formats.
- HTTP status codes.
- Migration impact on the frontend.
- Backward compatibility.

Use DTOs instead of exposing database entities directly.

Apply appropriate validation, centralized exception handling, safe logging and consistent response structures.

Do not return sensitive user fields in authentication responses.

#### E. MySQL and database integrity

Inspect the actual schema and implement necessary improvements:
- Unique constraints for normalized login identifiers.
- Indexes for authentication lookups.
- Parameterized queries or safe ORM operations.
- Appropriate transaction boundaries.
- Database migrations.
- Connection timeouts and pool configuration.
- Safe handling of duplicate registration.
- Protection against connection exhaustion.
- Least-privilege database credentials.
- Backups and recovery considerations.

Do not execute destructive schema changes without explaining their impact.

Do not use Hibernate `ddl-auto=create` or `create-drop` in production.

Prefer version-controlled database migrations when compatible with the current project.

## 4. Performance Target: 1,000 Concurrent Login Requests

Treat 1,000 concurrent login requests as a performance requirement to validate, not a guaranteed capability.

### Load-testing tool

Use Grafana k6 unless the project already has a suitable load-testing framework.

Create separate test scenarios for:
1. Valid logins with unique synthetic test accounts.
2. Invalid credentials.
3. Gradual ramp-up to 1,000 virtual users.
4. A short, controlled login burst.
5. Sustained load at peak concurrency.
6. Login followed by representative authenticated API requests.
7. Recovery after a controlled overload or dependency failure.

Use a staging environment that resembles production.

Never load-test third-party identity providers or production users without explicit authorization.

### Required measurements

Capture:
- Requests per second.
- Successful logins per second.
- HTTP status-code distribution.
- Login success and failure rates.
- p50, p95 and p99 latency.
- CPU and memory utilization.
- JVM heap and garbage-collection pauses.
- Active, idle and pending database connections.
- MySQL CPU, connection count and query latency.
- Rate-limit responses.
- Timeouts and connection errors.
- Load-balancer latency and health-check failures.

Use unique synthetic accounts and account for rate limits. Do not reuse one account for all virtual users unless that is an explicitly separate concurrency test.

### Initial acceptance criteria

Propose measurable targets before testing, such as:
- p95 login latency below 500 ms.
- Unexpected HTTP 5xx error rate below 1%.
- All valid synthetic accounts authenticate successfully.
- No unauthorized access or cross-user data leakage.
- No uncontrolled queue growth or connection-pool exhaustion.
- Stable resource utilization at the target load.

Treat these as provisional goals. Adjust them based on infrastructure, password-hashing cost and actual business requirements.

A test passes only when its measured results satisfy the agreed criteria. Never fabricate benchmark results or claim that a test was run when it was not.

### k6 deliverables

Provide:
- A maintainable k6 script.
- Configurable target URL and test credentials.
- Synthetic-account setup instructions.
- Concurrency stages and peak duration.
- Authentication success assertions.
- Latency and error-rate thresholds.
- A separate burst-test configuration.
- Commands for running the tests.
- Guidance for interpreting failures and diagnosing bottlenecks.

Use environment variables for test credentials and avoid hardcoding secrets in committed scripts.
